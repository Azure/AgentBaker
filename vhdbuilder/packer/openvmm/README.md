# Package-based OpenVMM SNP MAP evaluation

**Unsigned evaluation only; not production confidential-container support.**
Ordinary AgentBaker templates, CLH defaults and pipeline routing remain
unchanged. This opt-in integration consumes host/runtime packages from
repositories configured by the image pipeline. It no longer accepts raw host
kernel/module/EFI bundles or a source-built OpenVMM binary.

## Package inputs

The build VM must have access to the approved repository snapshots/buddy
repositories containing:

- `kernel-mshv`, with normal SNP injection and unmap-first teardown support.
- Matching `mshv`, `mshv-bootloader-lx` and `mshv-kd` packages.
- `openvmm`, including the confidential-only low-ECAM fix.

The installer uses `dnf`, matching ordinary AgentBaker repository handling,
to install/upgrade these package names, then checks their exact installed
epoch/version/release/architecture against `bundle.json` and verifies RPM payloads.
Configure repository snapshots/priorities to resolve those versions; a mismatch
fails the build instead of silently accepting a different stack. Kernel module
indexes regenerated by depmod are reported separately; EFI modes/timestamps
are not reliable on FAT. For an explicitly approved unsigned buddy evaluation,
only the dedicated evaluation repository may disable RPM signature enforcement.
Keep TLS verification enabled, verify downloaded artifacts against recorded
SHA256 hashes, and leave ordinary repositories' signature policies unchanged.

`kernel-uvm-cc` is an input to the **IGVM builder**, not a substitute for an
IGVM. That builder consumes `/usr/share/kernel-uvm-cc/bzImage` and regenerates
production/debug images against the matched rootfs verity inputs. Record its
package identity and the source-built generator/bootshim provenance. Buddy
repositories and credentials are provisioned outside these scripts.

## Remaining artifact bundle

MAP builds this installation bundle from its pinned Kata producer/runtime
source and guest/runtime buddy RPMs. It builds the generator/bootshim and
both IGVMs in its UVM stage, rather than downloading prebuilt private IGVMs.
Measurements and checksums must describe that run's newly built outputs.

Supply nonempty regular files without symlinks:

```text
artifacts/
  containerd-shim-kata-v2
  kata-openvmm-snp.bin
  kata-openvmm-snp-debug.bin
  kata-containers.img
  configuration-openvmm-azure-snp-runtime-rs.toml
  configuration-openvmm-azure-snp-runtime-rs-debug.toml
  containerd
  ctr
  mkfs.erofs
  bundle.json
  SHA256SUMS
  measurements/<native production/debug JSON, CBOR, ID-block files>
```

`SHA256SUMS` must cover every bundle file except itself. Checksums and package
version labels are not signatures, endorsements or proof of workload-policy
parity. Do not put proprietary payloads or credentials in this repository.
The former `host-components.json` and
`OPENVMM_TRUSTED_HOST_MANIFEST_SHA256` contract is no longer used.

## Installation and boot

Normal dependencies supply `kata-packages-host`, its existing `HvLoader.efi`,
and the stock Dom0 generator. This integration uses `dnf` for the pinned
kernel/MSHV/OpenVMM packages, retains or generates the matching initramfs,
and verifies kernel module availability.

The packaged MSHV driver is named `mshv_root`; checks must not assume a
module named `mshv` merely because the device is `/dev/mshv`.

`grub-menuentry.sh` reuses the stock Dom0 generator's root/kernel discovery
under a separate `OpenVMM SNP` entry and adds `MSHV_FORCE_NESTED=TRUE`. The
package-owned generator is not edited. Before reboot, the installer verifies
the selected kernel/initramfs and required SNP/nested-root flags. A GRUB
configuration that selects a different kernel fails instead of booting silently.

The package-managed `/usr/bin/openvmm` is exposed through
`/opt/kata-openvmm/bin/openvmm`; it is not overwritten from the artifact bundle.
Other runtime artifacts remain under `/opt/kata-openvmm`.

The existing Packer reboots and capture sequence are preserved. Packer runs
`check-image.sh` to check installed packages, kernel/module files and runtime
tool capabilities without requiring SNP-capable build hardware.
`check-host.sh` belongs to the resulting-image CC-node validation stage:
it additionally requires a changed boot ID, exact running kernel, expected
Hyper-V version/root partition/SNP availability, `/dev/mshv`, loops and DM
targets. These are prerequisites, not a guest-launch or attestation-chain test.
Modules are loaded through the image's `modules-load.d/openvmm.conf` at boot.
The host gate only checks them; it does not load missing modules, restart
services, fix configuration, or relabel nodes.
Booting the refreshed nested Hyper-V path on the ordinary MAP build SKU
still needs real image-build validation; there is no speculative boot deferral.

## Runtime and containerd

The shim must include OpenVMM support. Configs select `openvmm`, static sandbox
resource management, boot defaults of 1 CPU/1024 MiB and matching static workload
defaults. The separate `overhead_vcpus` and `overhead_memory` keys are zero.
Do not set `default_memory=0`: OpenVMM validates boot defaults before applying
pod resource limits. Debug selects the debug IGVM; production must not enable
diagnostics. The dynamic IGVM's temporary `clearcpuid=rdpid` workaround and
the longer CreateVM timeout needed for 32-GiB tests remain separate runtime
integration considerations.

After node provisioning, apply the Kata image builder's `runtimeclass.yaml`.
Its `kata-openvmm` handler matches this integration and reserves pod memory
overhead for the host VMM/shim. A pod memory limit without that headroom can
OOM-kill OpenVMM while guest RAM is being allocated; the Kubernetes overhead
must not be confused with the zero guest-sizing overhead knobs.
The opt-in image also maps the existing MAP `kata-cc` handler to that same
OpenVMM runtime/config, so existing Kata-CC RuntimeClass and test routing
remain usable. This alias is installed only for the explicit refresh, not
ordinary CLH images.

The opt-in containerd fragments require host EROFS transfer pulls,
`enable_dmverity=true`, `enable_tar_index=false`,
`mkfs_options=["-T0","--mkfs-time","--sort=none"]`,
`use_local_image_pull=false`, and explicit EROFS differ selection.
`default_size="0"` must have audited unmerged-directory semantics.
`dmverity_mode="on"` is enabled only when supported. Required capability
checks remain in place; packaging alone does not prove compatibility.

The default diff service uses `["erofs", "walking"]`, in that order.
AgentBaker's ordinary `ctr images mount` prefetch can unpack into overlayfs;
an EROFS-only default breaks that operation. Containerd tries the next differ
only for `NotImplemented` (such as EROFS rejecting a non-EROFS mount), not for
arbitrary extraction/integrity failures. Kata-CC transfer unpack still explicitly
selects `snapshotter="erofs"` and `differ="erofs"` with dm-verity enabled.
This is mixed-snapshotter compatibility, not a temporary integrity bypass.

These settings affect the evaluation node, not ordinary images. Complete
old-kata-cc policy/hash-binding parity and report signature-chain validation
are still separate work.

### Temporary protection against live CSE configuration replacement

Building this AgentBaker branch does **not** deploy its server-side code into
AKS RP. Legacy RP-supplied CSE can replace `/etc/containerd/config.toml` with
a config lacking the OpenVMM imports, even when the image-baked node-controller
templates have them.

The opt-in service drop-in therefore runs `containerd_config.py` before each
containerd start. It preserves the generated configuration and unrelated
imports, replaces only the owned import entry, and selects the fragment for
the root schema (version 2 versus versions 3/4). It uses the installed
containerd binary to load/migrate/merge a candidate in the same directory,
then checks both runtime handlers and the EROFS integrity settings before
atomically replacing the original file, retaining its permissions/ownership.
Malformed configs, missing fragments, disabled required plugins and conflicting
effective settings fail startup; there is no permissive fallback.

This is **temporary image-side workaround code** until every supported live
RP/ANC provisioning path preserves the same runtime contract. Remove the hook
only after that is verified; keep the read-only acceptance checks. It does
not copy the historical CLH/tardev repair script or change ordinary images.

Only the installer can explicitly initialize a missing build-machine config
from containerd defaults. Normal startup refuses a missing config. The service
declares its `/run/kata-openvmm` directory through systemd and regenerates a
configuration fingerprint on every start, rather than depending on a directory
or receipt left by Packer. The host gate checks the fingerprint against the
current effective config, the service's running binary/config arguments, and
live CRI/EROFS plugin health. Configuration values are not printed because
they can include registry credentials.
The live check reads the migrated v4 gRPC server-plugin address emitted by
containerd 2.3.3, with support for the older `[grpc]` layout as well.

The remote replay tests cover legacy configs without imports, the ANC import
form, schema changes, unrelated/nested imports, repeated CSE replacements,
cleared `/run` state, and failure without modifying the original configuration.
They do not substitute for first boot, live AKS CSE, or a fresh-node reboot.

## Resource and execution boundary

Host package installation requires explicit test-only opt-in and IMDS checks
for the exact temporary Packer VM and resource group derived from the MAP
build ID in the MAP test subscription. The controller must not run the installer.
`prepare.py` consumes MAP's existing generated settings and preserves the
builder's authentication, networking, SKU, image destination, and capture
configuration. It names only the temporary group/VM as
`pkr-openvmm-<build-id>` / `openvmm-<build-id>` for the installation guard.
Preparation itself makes no Azure calls.

Use the existing Kata build SKU (`Standard_D4ads_v5`) for assembly and the
separate opt-in CC-node test job for hardware validation. Review MAP's actual
gallery/image destination and resource effects before queuing; disabling
`publishVHD` does not prevent Packer from creating a gallery image version.

```bash
python3 vhdbuilder/packer/openvmm/prepare.py \
  --allow-unsigned-test-artifacts \
  --artifacts /absolute/path/to/artifacts \
  --map-settings vhdbuilder/packer/settings.json \
  --build-id 123456 \
  --output /absolute/path/to/eval-packer.json
```

Standalone preparation requires a new output path. MAP preparation with
`--map-settings` and `--build-id` permits task retries to reuse only a
byte-identical generated template after validating the current bundle and
settings again. Differing output, symlinks and output from another build are
rejected without overwriting them. This handles preparation retries after
transient Packer failures; it cannot resolve Azure quota exhaustion.

Secure Boot/vTPM/ConfidentialVM settings
and production signing are not established by this evaluation flow.
After reviewing MAP's settings, preparation alone can be exercised with:

```bash
make -f packer.mk prepare-openvmm-test \
  OS_SKU=AzureLinux OS_VERSION=V3 ARCHITECTURE=X86_64 \
  HYPERV_GENERATION=V2 FEATURE_FLAGS=kata \
  OPENVMM_UNSIGNED_TEST_ONLY=true \
  OPENVMM_ARTIFACT_DIR=/absolute/path/to/artifacts \
  BUILD_ID=123456
```

This target only generates the template. `build-packer` executes Packer and
requires separate approval of the complete resource/repository plan.
Repository setup must preserve TLS verification (`sslverify=1`). With explicit
approval for unsigned buddy RPMs, the dedicated evaluation repository may use
`gpgcheck=0`; do not use global `--nogpgcheck` or change other repositories.
Record the buddy run IDs, RPM hashes, and resolved package versions. These
checks are evaluation provenance/integrity checks, not package signatures.
Repository hosting, credential handling, and Azure resource creation still
require a separately reviewed execution plan.

Run the contract tests on the remote validation machine from AgentBaker root:

```bash
CONTAINERD=/path/to/evaluated/containerd \
  python3 -m unittest discover -s vhdbuilder/packer/openvmm -p 'test_*.py'
```

Set `CONTAINERD` to the actual bundle binary to execute the configuration
replay cases; without it those cases are explicitly skipped.

The privileged differ regression uses a generated, local OCI archive and a
separate daemon/store to reproduce the EROFS-only prefetch failure, then checks
ordinary prefetch and explicit EROFS transfer unpack with the corrected config.
Run it only on the remote validation machine, in a private mount namespace:

```bash
sudo env CONTAINERD=/path/to/evaluated/containerd OPENVMM_DIFFER_INTEGRATION=1 \
  unshare --mount --propagation private \
  python3 -m unittest discover -s vhdbuilder/packer/openvmm -p test_differ_integration.py
```

It requires the matching `ctr` beside `containerd`, `mkfs.erofs`, `fsck.erofs`, and host
snapshotter prerequisites. The test verifies the effective listener paths
before starting its daemon, isolates `/run`, and cleans up its backing mounts.
It refuses to run in the host's mount namespace. It inspects the unpacked EROFS
layer with `fsck.erofs` rather than activating globally named dm-verity devices
that could collide with another daemon's snapshot IDs.
